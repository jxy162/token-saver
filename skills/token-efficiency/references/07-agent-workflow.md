# 07 智能体工作流卫生：省在工具与上下文之间

智能体的 token 账单主要不是"提示词写得好不好"，而是**每轮往上下文里灌了什么**。一次全量读文件 = 几千 token 永久留在上下文里，并且之后每一轮都要重新付一次。

## 首要规则：搜索先行，精确读取

| 不要 | 要 |
| --- | --- |
| 读整个文件找函数 | `rg -n "functionName" src/` 定位 → 只读命中行附近区间 |
| 打印整个日志 | `head -100`、`grep ERROR`、`wc -l` 先看规模与模式 |
| 全量 `cat package.json` | `jq '.dependencies' package.json` 只取需要的字段 |
| 贴整个 diff | `git diff --stat` 看范围，再只展开相关文件的 hunk |
| 反复读同一文件 | 读一次，把结论（文件+行号+要点）写进上下文/笔记 |

量化：一次"读 800 行文件"约 8k~12k token；"rg 定位 + 读 30 行"约 300 token。**差 30 倍**，而信息量往往相同。

## 工具输出治理：在工具层截断，而不是让模型忽略

- 工具封装里就加上限：`head -n 200`、`--max-count 50`、`jq '.[0:20]'`、`git diff --stat`。
- 长输出先聚合再回灌：错误日志 → "共 1432 行，按类型统计：connection refused ×1204, timeout ×228"。
- 二进制/大文件：先看大小与类型，再决定是否读取。
- 需要全量时**写明为什么**，并把结果写到文件、只在上下文里留路径与摘要。

## 子代理/子任务：把"搜索+阅读"外包出去

把探索性工作丢给子代理，只回收：**结论 + 文件路径 + 行号 + 必要的片段**（几十 token），而不是它读过的所有内容（几万 token）。

适合外包：跨目录搜查、批量文件审读、方案可行性调研、长日志分析。
不适合外包：需要连续编辑同一批文件、需要精细上下文的任务（交接成本高于收益）。

## 会话与状态卫生

- 长任务按阶段开新会话/新线程：用"结构化交接"（见 03 的状态外部化）替代"把全部历史带着走"。
- 计划与结论落文件（`plans/*.md`、检查清单），上下文里只留指针。
- 不要在同一会话里既做探索又做实现：探索阶段的候选方案与失败尝试会一直占着上下文。

## 规则文件（AGENTS.md / CLAUDE.md）怎么写得省

规则文件**每一轮都在上下文里**，所以它是最贵的文档。只写：

- 非显然的约定（构建/测试命令、目录约定、特殊禁忌）
- 需要反复提醒的边界（"不要改 generated 目录"）
- 指向更详细文档的指针（"规范见 docs/style.md"）

不要写：通用最佳实践、模型本来就会的东西、长长的代码风格清单。这些既涨 token 又稀释注意力。经验值：**规则文件控制在 1 页内**；超出部分移到按需读取的文档。

## 技能/提示模板：渐进披露

把技能写成三层：短入口（何时用、怎么做）+ 按需加载的参考文件 + 确定性脚本。
- 入口短 → 每次进入上下文都便宜。
- 细节放参考文件 → 只有真需要时读。
- 脚本执行不占上下文（只回结果），比"让模型复述一遍算法"省得多。

## 循环控制：重试是最贵的操作

一次失败重试 = 全额重复计费（含全部历史与工具输出）。所以：

- 设重试上限（例如同一策略最多 2 次），失败就**换策略**而不是重试同样输入。
- 重试时先裁剪上下文：失败的中间输出通常只需要错误摘要，不需要全文。
- 幂等操作（读取、查询）可以放心缓存；有副作用的操作要幂等键，避免重复执行。

## 检查清单

- [ ] 是否用搜索/统计代替了整文件/整日志读取？
- [ ] 工具输出是否有硬上限与过滤？
- [ ] 探索性工作是否外包给子代理，只回结论？
- [ ] 规则文件是否只写了非显然约束？
- [ ] 长任务是否有检查点文件，而不是靠上下文记忆？
- [ ] 重试是否有上限，且失败时换了策略？
