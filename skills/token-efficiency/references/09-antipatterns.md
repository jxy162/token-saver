# 09 反模式：token 泄漏清单

逐条对照。每条给出"为什么浪费"与"怎么改"。

1. **每轮重发全部历史**：多轮对话成本近似平方增长。→ 压缩（03）+ 前缀缓存（04）+ 状态外部化。
2. **稳定区放时间戳/随机 ID**：前缀缓存 100% 失效，等于白付全量。→ 挪到尾部或删除。
3. **动态排序的内容放在前缀里**：`Object.keys()`/集合遍历顺序不稳定 → 每次前缀都不同。→ 显式排序序列化。
4. **用大模型做正则能做的工作**（分类、格式转换、去重、计数）：价格差 10~50 倍。→ 代码/小模型/embedding。
5. **工具输出整块回灌**：一次 10k token，并且之后每轮重复计费。→ 工具层截断、过滤、聚合（07）。
6. **检索 top-20 全塞进去**：噪声多、成本高、准确率反而降。→ 先重排再截断到 1~5 条（05）。
7. **没有 `max_tokens`**：模型自由发挥写长文。→ 按输出 p95×1.2 设定。
8. **"请详细解释"却不给长度上限**：输出膨胀 30%~50%。→ 明确字数/字段上限。
9. **重试无上限、原样重发**：一次超时重试 = 全额重复计费。→ 重试上限 + 换策略 + 重试前裁剪。
10. **用 token 级压缩压指令/schema**：省 20%，但约束失效、返工更贵。→ 只压检索到的长文本。
11. **把 JSON 重复键塞进上下文**：数据块浪费 30%+。→ CSV/TSV 或列式。
12. **所有流量同一个旗舰模型**：简单任务付 30 倍价格。→ 规则路由 + 级联（06）。
13. **缓存键没归一化**：大小写/空白/参数顺序差异导致命中率虚低。→ 归一化 + 参数排序 + 版本号。
14. **缓存键不含 prompt 版本**：改了提示词还在吃旧答案。→ 版本号进键。
15. **不限制推理/思考预算**：推理 token 按输出计价且不可见。→ 分类/抽取类关闭或给极小预算。
16. **长会话不落检查点**：靠上下文记忆状态 → 上下文只能越滚越大。→ 状态写文件，上下文留指针。
17. **few-shot 照抄长文档**：示例比任务本体还长。→ 换成最短能说明"格式+边界"的例子。
18. **同一段内容中英双语各写一遍**：token 直接翻倍。→ 选定一种语言；术语可保留原文但不要整段重复。
19. **把检索片段里的元数据全带上**：`{"score":0.81,"source":"...","chunk_id":"...","publish_time":"..."}` 常比正文还长。→ 只留来源标识 + 正文。
20. **只看字符数估 token**：中英混排/JSON 误差可达 2 倍。→ 用真实分词或 `estimate-tokens.mjs`。
21. **缓存检索结果但不随知识库失效**：知识更新后答案陈旧。→ 知识库版本进缓存键。
22. **没有 label 埋点**：账单无法归因，优化无的放矢。→ 每次调用带 label（08）。
23. **把"省 token"做成一次性项目**：改完就反弹。→ 守门 + 告警 + 双回归（08）。
24. **静默降级**：为了省钱悄悄换小模型、悄悄截断上下文，用户只看到质量变差。→ 降级要可观测（日志/指标），必要时告知用户。

## 用法

审计时按此清单逐条打勾（有/无/不适用），把"有"的条目按 预期收益 ÷ 改动成本 排序，一次只改 1~2 条。
