# 03 上下文压缩：少带不必要的过去

## 什么时候该压缩

触发条件（任一）：

- 每轮输入 > 5k token，或占窗口 > 60%~70%
- 历史里超过一半内容与当前任务无关（已完成步骤的中间输出、被推翻的方案、重复的工具回显）
- 每轮成本随轮数线性上涨（说明历史在无脑累积）

**不该压缩**：任务需要精确回溯细节（审计、逐字改写）；历史里含不可再生的关键 ID 列表（应单独保留，而不是摘要掉）。

## 三种粒度

| 粒度 | 做法 | 工具/命令 | 典型收益 |
| --- | --- | --- | --- |
| 段级裁剪 | 按优先级把多段内容裁进预算 | `scripts/trim-context.mjs` | 一次请求立省 30%~90% |
| 历史摘要 | 旧轮次换结构化摘要 | 让模型生成（一次调用） | 每轮 -50%~80% |
| 状态外部化 | 结论/计划写进文件或记忆，上下文只留指针 | 工作流约定 | 长任务可达数量级 |

## 段级裁剪：用优先级而不是"先进先出"

输入（JSON）：

```json
{ "budget": 8000, "reserveOutput": 1024, "segments": [
  { "id": "policy",   "kind": "policy", "locked": true,  "text": "..." },
  { "id": "schema",   "kind": "schema", "locked": true,  "text": "..." },
  { "id": "diff",     "kind": "tool",   "locked": true,  "text": "..." },
  { "id": "docs",     "kind": "retrieval", "priority": 55, "minTokens": 200, "text": "..." },
  { "id": "history-1","kind": "history", "recency": 1, "text": "..." } ] }
```

```bash
node scripts/trim-context.mjs context.json --budget 8000 --reserve-output 1024 --out trimmed.json
node scripts/trim-context.mjs context.json --budget 8000 --print-text   # 直接拼成 prompt
```

规则：

- `locked: true` 的段（schema、工具定义、当前任务约束、精确数值）**只整体保留或整体丢弃，绝不截断**——截断一个 JSON schema 比丢掉它更糟。
- 其余段按 `priority` 降序保，同优先级按 `recency`（新的先留）。
- 放不下的可裁剪段按 `head-tail` 折中截断（保留开头与结尾，中间省略），并写进 report，便于事后审计"为什么这段没了"。
- report 里 `action` 为 `dropped`/`trimmed` 的条目就是本次的信息损失账本。

默认优先级：policy 100 / system 95 / task 90 / schema 80 / tool 60 / retrieval 50 / example 25 / history 20。

## 历史摘要：结构化模板

**不要**让模型自由总结（会丢约束、会幻觉细节）。用固定字段：

```
【任务目标】<一句话>
【已确认事实】<只保留可验证的结论，含精确 ID/数值>
【已尝试并排除】<方案 + 失败原因>
【未决问题】<待确认项>
【下一步】<明确的动作>
【必须保留的约束】<来自用户或系统的硬约束，逐条抄录>
```

要点：

- **ID/数值/路径不摘要**，原样抄录（摘要最容易在这里失真）。
- `必须保留的约束` 逐字保留，它是"压缩后答错"最常见的原因。
- 摘要本身要花一次调用（输入=旧历史，输出=摘要）。摊销计算：若旧历史 20k token、摘要 800 token、之后还有 10 轮，则每轮从 20k 降到 ~1k，第一轮就回本。
- 把"最近 N 轮原文"和"更早的摘要"一起带上，通常 N=2~4。

## 状态外部化（长任务最有效）

把中间结论写进文件（计划文件、检查清单、`NOTES.md`），上下文里只保留：

```
进度见 plans/migration.md（阶段 3/5）；已确认的接口清单在 plans/api.md。
```

这样即使换会话、换 agent，也能低成本恢复。比"把 40 轮对话留在上下文里"便宜一个数量级。

## 风险与对策

| 风险 | 对策 |
| --- | --- |
| 摘要丢掉关键约束 | 约束字段逐字保留；压缩后跑回归用例 |
| 摘要幻觉出错误事实 | 摘要只允许写"输入里出现过的"内容；保留 ID 列表原样 |
| 截断把代码/日志切断在中途 | 按行截断，不按字符；代码块整块处理 |
| 压缩成本超过收益 | 只在超过阈值时压缩；短会话别压 |
| 反复压缩同一段 | 记录压缩标记，避免二次压缩叠加失真 |

## 检查清单

- [ ] 预算是否包含输出预留（`reserveOutput`），而不是用满整个窗口？
- [ ] 结构化约束（schema/工具定义）是否 `locked`？
- [ ] 摘要里是否逐字保留了 ID、数值、硬约束？
- [ ] 是否保留最近 N 轮原文，而不是全部摘要化？
- [ ] 压缩后是否用同一批用例复测过质量？
