# 05 检索：注入什么，注入多少

RAG 的 token 账单几乎全在"注入了多少没用的片段"。检索质量与 token 成本是同一个问题的两面。

## 注入前必须过的四道闸

| 闸门 | 做法 | 效果 |
| --- | --- | --- |
| 重排（rerank） | 向量召回 20~50 条 → 交叉编码器/LLM 重排 → 取 1~5 条 | 比"加大 top-k"更省也更准 |
| 截断 | 每条片段限 200~500 token，超长按行截断 | 防单条吃掉预算 |
| 去重 | 近重复（同一文档多分块命中）只留一条 | 常省 20%~50% |
| 格式化 | 只带"来源 + 行号/段落号 + 内容"，不要再带元数据 JSON | 去掉无意义字段 |

**顺序很重要**：先重排再截断。先截断会切掉正确答案需要的上下文，反而需要更多片段来补偿。

## 数量与长度的经验值

- 片段数：1~5。超过 5 条后，答案质量提升很小，token 成本线性增长。
- 单片段：200~500 token。低于 200 常缺上下文，高于 500 通常含大量噪声。
- 总注入：控制在预算的 30%~50%，给输出和推理留空间（`reserveOutput`）。
- 分块大小与片段数要一起调：块越小，命中同样内容需要的片段越多。

## 让模型"按需取"而不是"一次全给"

分层注入（agentic retrieval）：

```
第 1 步：只给目录 —— 文档名 + 一句话摘要 + 行号范围（~200 token）
第 2 步：模型指出需要的 1~2 个区段 → 再注入这些区段的原文
```

相比"一次性注入 10 个片段"，通常省 5~10 倍，且答案引用更精确。代价是多一次往返。

## 表示形式

| 内容 | 省 token 的写法 | 避免 |
| --- | --- | --- |
| 表格 | CSV/TSV（表头一次） | 重复键名的 JSON（实测省 33%，数据越大越明显） |
| 代码 | 文件路径 + 行号区间 / unified diff | 整个文件 |
| 日志 | 过滤后的关键行 + 计数 | 全量堆栈 × N 次 |
| 长文档 | 相关段落 + 章节标题 | 全文 + "请自己找" |

## 缓存检索与中间结果

- 同一 query（归一化后）→ 同一片段集：直接缓存检索结果，省一次向量查询与一次拼接。
- 检索结果也要进结果缓存的键（否则知识库更新后还在用旧片段）。
- 高频 query 可以做"预检索 + 预热前缀缓存"。

## 什么时候不该用 RAG

- 任务需要**全局理解**（"这份合同有哪些风险点"）：检索只会给碎片，不如先做一次"文档摘要"再基于摘要问答。
- 知识量很小且稳定（< 2k token）：直接全量放前缀缓存，比检索便宜且更准。
- 需要精确计算的：给数据，不要给检索片段。

## 指标

- 每请求注入 token（p50/p95）
- 检索命中率 / 引用率（答案里引用的片段占比）
- 质量回归：同一批问题在"片段数从 5 降到 3"后通过率是否下降

## 检查清单

- [ ] 是否先重排再截断，而不是先截断？
- [ ] 片段数与单片段长度是否在经验区间内？
- [ ] 是否去掉了近重复片段？
- [ ] 表格/日志/代码是否用了紧凑表示？
- [ ] 能否改成"目录先行、按需取细节"？
